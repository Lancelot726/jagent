## 4 阻塞点（编码前必须先解）

**现状**：`Cli.java:86-90` 的客户端工厂对两档使用**同一份** `baseUrl` + `apiKey`：

```java
private static ChatClient client(Config cfg, String model) {
    return cfg.isMock()
            ? new MockClient(model)
            : new OpenAiClient(cfg.baseUrl, cfg.apiKey, model, 120);
}
```

`Config.java:77` 只提供了强档的**模型名**（`model-strong` / `JAGENT_MODEL_STRONG`），
没有强档的地址与密钥。因此当前只能"一家厂商的两个模型名"竞价，
**做不到作者要的"两个厂商"竞价**。

**最小改动**：`Config` 增强档地址/密钥三件套，`Cli.client()` 改为按档位取用。

## 8 机制对账单（本轮新增交付物的做法）

**问题**：R1 的四组机制在运行时各自打点（竞价一行、压缩一行、收尾一行），
一次真实运行结束后要人工翻屏拼接才能拼出"机制是否真的生效"的全貌。
真实厂商下一轮只有一两次机会，不能靠翻屏。

**做法**：新增 `jagent.agent.Scorecard`，在 `run` 收尾时把各机制的**计数型证据**
汇总成一块，同时落盘 `work/scorecard.txt`。所需计数在机制类原地累加（不新造第二份状态）：

| 机制 | 新增计数 | 来源 |
|---|---|---|
| 拍卖 | 各档中标次数 | `Auction` |
| 拍卖 | 累计利润、各档信誉 | `Auction`（已有 `profitTotal` / `reputation`） |
| 预算 | 消耗 / 上限 / 燃烧速率 | `Budget`（已有） |
| 压缩 | 压缩次数、累计省下 token | `Cli` 观察者（`onCompress` 已带前后值） |
| 控制论 | 上调 / 下调 / 熔断次数 | `Governor` |
| 控制论 | 并发峰值、路径互斥冲突 | `Admission`（冲突已有） |
| 降级 | 备用档切换次数、重试次数 | `FallbackClient` |
| 图工程 | 节点 / 完成 / 失败 / token | `Graph`（已有） |

约束：计数只增不改语义；不得改变既有判定逻辑与打印内容（R1 断言不得因此变红）。

**真实厂商验证结果（2026-09-20）**：两档真实配置投喂后，d1–d5 五个场景实跑，
四组机制全部在真实厂商下生效，且拍卖在同一次运行内发生了翻转。
证据件 `R2_51_real_vendor_evidence.wip.txt`；结论详见 `R2_94_rounds.md` 的 R2 节。

其中三处缺陷由真实实跑暴露（mock 不复现），已在本轮修掉：
思维链模型 `reasoning_content` 回传、`Admission.setLimit` 降额阻塞、嵌套许可死锁。
